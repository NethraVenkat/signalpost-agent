# X1 official role-update source review — 2026-11-14

Checked the [official open-data API documentation](https://data.brreg.no/enhetsregisteret/api/dokumentasjon/no/index.html), [role dataset description](https://www.brreg.no/bruke-data-fra-bronnoysundregistrene/datasett-og-api/roller-i-virksomheten/) and [dataset/licensing catalogue](https://www.brreg.no/bruke-data-fra-bronnoysundregistrene/datasett-og-api/). Public registry data follows NLOD; use only the open `/api/` endpoint. No Maskinporten, national identifiers, authenticated person lookup or commercial subscription is used.

`GET /enhetsregisteret/api/oppdateringer/roller` is documented as an array of CloudEvents. It accepts comma-separated `organisasjonsnummer`, `afterTime`, `afterId` and `size` (maximum 10,000). Default response size is 100; a shorter-than-requested page means the current feed is exhausted. The implementation requests 1,000 per page, batches at most 200 exact company numbers, uses a 36-calendar-month first cursor, then the maximum returned event ID as the documented after-ID cursor. It never follows arbitrary next/source URLs. Global budget, existing registry timeouts/retries and per-host concurrency still apply. No API call bypasses a 401/403 or moves to an authenticated route.

Two bounded diagnostic HTTP attempts are in `X1-probe.json`: robots request ended with a ReadError, and the public role batch returned 200. This uses the project's existing licensed public registry REST policy, distinct from website-crawler robots failure handling. No registry website crawl or protected route was used. Diagnostic requests are separate from the six mandatory fresh-state runs; provider cost $0. Source body/hash/time and exact batch URL are saved.

The saved live batch contains 237 role events. Every `data` object contains only `organisasjonsnummer`. Types include `no.brreg.enhetsregisteret.rolle.oppdatert` and `no.brreg.enhetsregisteret.rolle.enhet.oppdatert`. The public feed gives no changed role type, appointee, departure, person name or effective date. Therefore X1 can honestly publish generic dated role-registry updates, with the exact event type and publication time, but cannot identify daglig-leder/styreleder changes or prefer an alleged leadership change. It never joins the current role roster onto a past generic event to invent what changed. Role/person detail states stay explicitly not supplied. The displayed date is **registry publication time, not effective date**.

Full evidence reconstructs the source event and its ID/type/time/source/company fields. Role events share the existing newest-50 registry-event cap; event IDs use source namespaces so a role-event ID cannot collide with an entity-event ID. Exact duplicates deduplicate; conflicting IDs, repeated cursors, invalid timestamps and wrong-company records fail explicitly. Events published after run start remain outside that run's snapshot. No new person name is published by X1.
